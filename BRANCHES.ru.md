# Две линии MYBOXES INAV

## Что где находится

| Ветка | Исходная база | Уже выпущено | WSL: проект / исходники |
|---|---|---|---|
| inav-9 | INAV 9.1.0, e519b69b | r15 Stable | ~/inav/mybox / ~/inav |
| inav-10 | INAV 10.0.0-rc2, f1cd5c6f | r16 Dev | ~/inav-10/mybox / ~/inav-10 |

Обе линии содержат все три платы. Ветка по умолчанию — inav-10.
main оставлена для старых ссылок и истории. Не вносите в неё новые исправления и не запускайте из неё релиз.
Релизные теги и ранее скачанные HEX не менялись. Названия релизов включают версию INAV, поэтому выпуски 9 и 10 не конфликтуют.
Stable/Dev — степень проверки конкретного выпуска; ветка inav-9 сама по себе не делает каждый новый коммит Stable.

## Работа каждый день

Для версии 9:

```bash
cd ~/inav/mybox
git switch inav-9
git pull --ff-only
bash build.sh ~/inav
```

Для версии 10:

```bash
cd ~/inav-10/mybox
git switch inav-10
git pull --ff-only
bash build.sh ~/inav-10
```

Не переключайте версии 9/10 в одном каталоге исходников: у каждой есть собственные патчи и каталог сборки.
Не копируйте целиком драйверные патчи между версиями.
При сообщении о несовпадении файлов сохраните локальные правки; не применяйте reset/clean для их удаления.
Для полностью чистой сборки можно передать build.sh новый отсутствующий каталог, например ~/inav9-clean или ~/inav10-clean, из нужной ветки проекта.

Временные ветки исправлений создавайте от нужной линии, например codex/inav9-sd-fix или codex/inav10-can-fix.
Pull request должен идти обратно в ту же линию. У каждой линии свои автоматические сборки трёх плат и тесты.

## Если исправление нужно обеим версиям

1. Исправьте и проверьте его в одной версии.
2. Перенесите конкретное изменение во вторую отдельным коммитом. Если код совместим, подходит git cherry-pick.
3. Если меняется board-support.patch или старые патчи 9.x, адаптируйте изменение к исходникам второй версии и проверьте его заново.
4. Соберите все три платы и выполните проверки этой линии.

Не сливайте inav-10 целиком в inav-9 и наоборот: это заменит основу INAV.
Исправление одной ветки не считается автоматически проверенным во второй.

## Как выпустить обновление

1. Откройте Actions → Publish Mini firmware (INAV 9 or 10).
2. В Run workflow выберите нужную ветку: inav-9 или inav-10. Скрипт берёт правила из выбранной ветки.
3. Укажите новую ревизию. Следующие свободные после текущих выпусков: для 9 — r16, для 10 — r17. При следующем выпуске проверьте, что такой тег ещё не занят.
4. Запустите. Сценарий проверит линию, соберёт три платы, выполнит тесты и опубликует три Dev-релиза с HEX, манифестом и SHA-256.
5. Сайт получает релизы общего репозитория. Разделение веток не меняет адреса скачивания или работу MyboxDiag.

Run workflow читает workflow из выбранной ветки: перед запуском всегда проверьте поле Branch.
Все три манифеста содержат source_branch, inav_major, upstream_release и точные коммиты проекта/INAV.
Чужая ветка или исходный коммит не проходят проверку перед публикацией.
Новый выпуск публикуется как Dev. Перевод в Stable выполняется отдельно после проверки на платах с сохранением байтов и SHA-256 проверенного HEX, как для r15.
Не пересоздавайте уже опубликованные теги и не заменяйте файлы старого релиза.

## Обновление версии INAV внутри линии

release-line.json хранит тег и полный коммит официального INAV. При обновлении измените оба значения, адаптируйте патчи и повторите проверки.
Число inav_major должно совпадать с именем ветки и тегом. Переход с 9 на 10 выполняется в ветке inav-10.

Локальные каталоги полных исходников содержат применённые правки и могут включать отдельную диагностику. Их содержимое само по себе не является опубликованным релизом:
состав повторяемой сборки задают зафиксированный upstream и файлы соответствующей ветки проекта.
